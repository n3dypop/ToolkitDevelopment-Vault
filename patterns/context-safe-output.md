# 出力先の文法と文字位置を契約にする

## 使う条件

同じデータから端末、HTML、スクリプト、JSON など複数形式へ出力したり、Unicode の位置を外部 API へ渡したりするときに使う。

## データと制御を分ける

- 内部の結果モデルを出力形式から分け、各 serializer が出力先の文法を担当する。
- グリフやユーザー入力を、出力先に合う規則でエスケープする。一つの形式用の変換を別形式へ流用しない。
- 色や寸法など、構文を組み立てる値は検証済みの型・数値から生成する。入力のファイル名や文字列をそのままテンプレートや制御列へ挿入しない。
- 通常の文字出力と、端末の制御シーケンスを明示的に分ける。入力文字として許す制御文字・結合文字・表示幅の条件を決める。
- 外部コマンドへ渡すパスや値は、可能ならシェル文字列へ連結せず引数列として渡す。出力用のエスケープとプロセス起動時の引数処理を混同しない。

## 文字位置の単位

byte offset、Unicode のコードポイント、書記素、端末カラム数は別の単位である。長さ、切り出し、ハイライト範囲で何を使うかを入出力契約に書く。

出力先が UTF-8 byte offset を要求するなら、文字数や表示幅から流用せず、実際に出力したバイト列へ対応させる。グリフの置換やエスケープで長さが変わる場合も、どの段階の位置かを区別する。

## 互換性と失敗

構造化出力には、必要に応じて版、任意フィールド、省略時の意味を定義する。表示で使わない情報でも、ライブラリや JSON の契約で返しているなら、最適化を理由に捨てない。

許さない文字や組合せは、出力を一部書いてから気付くより、可能な範囲で先に検証する。失敗時に既存の結果を保持するか、途中出力を破棄するかも決める。

## 使わない条件

一つの標準 serializer だけで契約を満たせる場合、独自の汎用エスケープ基盤を追加しない。任意の Unicode を扱う必要がある用途へ、単一カラム文字だけという制約を持ち込まない。

## 確認方法

- 引用符、バックスラッシュ、改行、制御文字、結合文字、全角文字、非 ASCII を対象にする。
- 出力を parser や利用側 API で読み、内容と位置範囲を照合する。
- 省略フィールド、前景・背景、色のリセット、形式ごとの代替表現を確認する。
- 構造検査だけで実クライアントでの表示まで確認したと表現しない。
