# 出力契約を守る性能改善

## 使う条件

変換、描画、シリアライズ、デコードなど、既存の出力を保ちながら速度やメモリを改善するときに使う。

## 比較する契約を先に固定する

- 基準版と候補版、入力、ビルド条件、依存関係、ハーネスを識別できるようにする。
- 文字列・画素・寸法・順序・時刻・エラー・保存内容など、何を同一とするかを決める。
- 時間値など一致しない診断を除く場合は、除外フィールドを限定する。意味の差まで除外しない。
- JSON の意味的一致と全バイト一致を区別する。表記や順序も契約なら、意味的一致だけでは足りない。
- 最適化した関数だけでなく、呼び出し元の所有・借用・バッファ再利用の経路でも比較する。

## 測定面を分ける

| 測定面 | 含むもの | その結果だけでは言えないこと |
| --- | --- | --- |
| core | 変換・整形など限定した処理 | 起動や I/O を含む全体の速度 |
| process | 起動、読込、処理、出力 | 表示装置での描画や利用者の体感 |
| resource | 確保回数、保持容量、RSS など | 他の種類のメモリ指標や全プロセス合計 |
| device | kernel、転送、初回初期化 | 端末全体や別機種の性能 |

測定区間に flush、永続化、待機、子プロセスが含まれるかも記す。別々に測った段階の中央値を足したり、過去の速度比を掛け合わせたりして総合性能としない。

## 採否を決める

1. 同等性と既存の上限・失敗処理を確認してから測定する。
2. 小入力、同寸法、拡大・縮小、透過、低色数・多色数、上限近傍など、経路が変わる条件を選ぶ。
3. 冷間とウォームを分け、反復・実行順・集計方法・生サンプルを残す。微小処理は測定自体の費用を考慮する。
4. 改善した経路と悪化した経路を併記し、利用者が通る全体経路で採用の利点を確認する。
5. 試作だけ速い変更や、再利用 API で悪化する変更は取り下げるか、条件を絞る。

再利用バッファは確保を減らしても最大容量を保持し得る。キャッシュには上限と従来経路への復帰を持たせ、上限を超える入力でも出力契約を守る。

## 使わない条件

出力品質や形式を意図的に変える場合は、同等性を装わず別の受け入れ条件を定義する。性能が要件でない軽微な変更へ網羅的なベンチマークを課さない。

## 確認方法

- 基準版との出力比較と異常系が通る。
- 試作、採用版、通常の配布構成での結果を区別できる。
- 実測していない環境や機器へ高速化率を一般化していない。
- 悪化・ばらつき・不採用案が結論から隠れていない。

[証拠と検証](../guides/evidence-and-validation.md)と併用する。[ソース台帳](../catalog/SOURCES.md)の SRC-010 から抽出した判断であり、新しい案件での性能や互換性を保証するものではない。
