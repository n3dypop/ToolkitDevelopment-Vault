# 作業領域と公開境界

## 三つの領域

成果物は役割で分離する。

| 領域 | 内容 | 原則 |
| --- | --- | --- |
| 原本 | ユーザー提供データ、取得物、基準版 | 読み取り専用。最初に識別情報を記録する |
| 作業領域 | 抽出物、実験、診断、比較、ログ | 再生成可能にし、公開物へ混ぜない |
| 公開領域 | ソース、必要なテスト、利用文書、ライセンス | 単独で利用・検証できる最小構成にする |

`.gitignore` で外部の非公開領域を指し示すのではなく、物理的にリポジトリ外へ分ける。公開に必要なテストと、研究用の大量データや独立診断は区別する。

## 公開前の監査面

現在の作業ツリーだけでは足りない。少なくとも次を確認する。

- tracked、staged、untracked の全ファイル
- 到達可能な Git 履歴とタグ
- symlink、submodule、埋め込みリポジトリ
- 配布 ZIP、インストーラー、生成 manifest
- `.env`、鍵、証明書、token、ユーザー名、絶対パス
- 第三者ライセンス、NOTICE、フォントや素材の再配布条件

監査ツールは秘密らしい文字列を検出しても、その本文をログへ再出力しない。公開物の許可リストと件数、パッケージ展開後の構造も確認する。

## ローカル完了と外部工程

ローカルで完了できることと、資格情報、費用、組織登録、外部送信を伴う工程を分離する。

- ローカル: build、static check、package structure、hash comparison、unsigned state の確認
- 外部: signing、store submission、dashboard upload、第三者審査
- 返却後: 署名や変換で内容が変わる前提の再検証、実環境での導入試験

外部工程が残っている場合は「提出前まで完了」と表現し、配布可能・署名済み・実機確認済みとは書かない。安全機能を無効化して外部工程を代替しない。

## 履歴の整理

公開履歴を作り直す必要がある場合、元の履歴を回復可能な形で保持し、退避物自体の完全性を確認する。ユーザーの明示承認なしに既存履歴を書き換えない。公開用の新しい履歴には、退避先の内部名や非公開構造を推測できる痕跡を残さない。
