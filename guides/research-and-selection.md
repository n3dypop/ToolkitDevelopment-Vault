# 調査を採用判断へつなぐ

## 調べる範囲

技術選択、命名、依存追加、拡張案など、判断によって成果物が変わる場合に使う。軽微な修正へ類似製品調査を一律に要求しない。

既存ツールの目的、README、マニフェスト、関連する実装、ビルド条件、許諾表示を必要な範囲で読む。対象版を固定し、紹介文での主張と、コードから確認した挙動と、実行して測った結果を分ける。

人気や更新日の一つの値だけで採否を決めず、自分の用途との一致と実際の制約を確認する。調査した機能を、実装済みの機能として報告しない。

## 比較して決める

| 観点 | 確認すること |
| --- | --- |
| 利用価値 | 誰のどの利用経路を改善するか |
| 工数と不確実性 | 成立性を左右する部分を小さく試せるか |
| 実行依存 | 利用者に追加導入や特殊環境を要求するか |
| 互換性 | 既存の API、形式、既定値、明示設定へ影響するか |
| 保守 | 構成や対応環境の数に見合う利点があるか |
| 根拠 | 実測、コード確認、仮説のどの段階か |

単純なファイル操作など、既存環境の標準機能で十分な処理は、その機能を優先して検討する。共通実装へ集約することで利用者のランタイム依存が増える場合は、コードの重複削減だけで採用を決めない。複数実装を選ぶ場合は、共通の受け入れ条件とテストで振る舞いを揃える。

新しい機能や高速経路は、低コストで同じ結果を保てる改善、実際の主要経路、未解決の機器依存という順序など、根拠に沿って優先する。未測定の並列化や特殊ハードウェアを、既定で高速な方式と扱わない。

## 参考にすることと取り込むこと

方式や API を調べること、実行依存として使うこと、コードや素材を複製・同梱することを別の判断にする。宣言上のライセンス名だけで転載を決めず、採用方法に必要な本文・表示・由来を確認する。不明な原文や素材を Vault へ持ち込まない。

## 命名と変更

表示名、リポジトリ名、パッケージ名、コマンド名を分け、用途の伝わりやすさ、検索時の混同、入力のしやすさを確認する。検索結果は調べた検索面と時点に限られる。

名称が決まったらマニフェスト、ソース、ヘルプ、配布名、生成物の識別名、ワークフロー、文書を揃える。過去の生データ、hash、ビルド情報は当時の記録として保持し、改名そのものを性能改善へ数えない。

## 記録の置き場所

候補一覧、調査時点、固有値、実験結果は案件側へ置き、Vault には判断軸、適用条件、除外事項を残す。採用理由は設計、実行結果は検証、次の候補は計画へ分ける。

[文書システム](document-system.md)、[証拠と検証](evidence-and-validation.md)、[配布物の検証](artifact-verification.md)と併用する。[ソース台帳](../catalog/SOURCES.md)の SRC-017 を参照する。
