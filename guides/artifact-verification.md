# 配布物の由来と単独利用を確かめる

## 適用範囲

ソース以外にパッケージ、バイナリ、アーカイブを配る場合に使う。ソース公開だけの変更へ、全ターゲットの配布試験を強制しない。

## 由来の鎖を閉じる

`source revision → manifest and lock → build → packaged bytes → installed behavior`

- タグから作る場合は、タグの版、マニフェストの版、タグが指す commit、checkout の HEAD を照合する。
- バイナリやパッケージ自身の版表示、配布名、対象 OS・CPU・機能構成も照合する。
- ビルド元、ツールチェーン、対象構成、必要な hash を manifest に記録する。内部パスや資格情報を記録しない。
- 保管済み配布物の manifest は、後からソースの履歴や名称が変わっても書き換えない。再ビルドしたものは別の成果物として識別する。

hash の一致は対象バイトの同一性を示すが、発行者の正当性や実行時の安全性を単独では証明しない。

## アーカイブから確認する

1. ソースの構成と別に、配布経路ごとにメンバー一覧と必要ファイルを検査する。
2. 設定、実データ、DB の付随ファイル、ログ、画像、内部資料が入っていないことを確かめる。
3. 対象構成で実際に同梱する依存物と、必要なライセンス・NOTICE を照合する。別途導入する依存と同梱物を区別する。
4. 別の一時領域へ展開またはインストールし、公開された手順だけで最小の利用経路を実行する。
5. ソース配布物もあるなら、その内容だけから再ビルドできるか確認する。

ライセンス本文の補完は確認済みの版と由来に限定する。不明なものを似た依存の本文で代用しない。

## 再現性と対応環境

メンバー内容が一致すること、アーカイブ全体のバイトが一致すること、再実行できることを区別する。圧縮時刻などでアーカイブが異なる場合は比較面と除外理由を記録する。

クロスコンパイル、型検査、中間表現の生成は、対象 OS や実機での動作確認の代替にならない。必要な外部コマンド、ランタイム、署名・公証、機器、プラットフォーム制約を、検証済みと未検証に分ける。

## 公開直前と公開後

作業ツリー、コミット済みファイル、配布物を照合し、最後の変更後に必要な検査を行う。公開が依頼に含まれる場合は、ローカル commit とリモートの参照、公開された asset を別々に確認する。

[作業領域と公開境界](workspace-and-publication.md)、[証拠と検証](evidence-and-validation.md)、[配布検証テンプレート](../templates/RELEASE.template.md)と併用する。[ソース台帳](../catalog/SOURCES.md)の SRC-008、SRC-011 を根拠とし、個別の配布先の要件は採用時に確認する。
