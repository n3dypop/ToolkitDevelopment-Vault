# 文書システム

## 文書は時間軸で分ける

一つの巨大な文書へ規則、設計、進捗、検証結果を詰めると、古い事実が恒久ルールに見える。内容が変わる速さと責任で分ける。

| 問い | 置く文書 |
| --- | --- |
| エージェントはどう行動するか | `AGENTS.md` |
| 何を、なぜ、この構造で作るか | `DESIGN.md` |
| どの条件で何を確認したか | `VALIDATION.md` |
| いまどこまで進み、何から再開するか | `HANDOFF.md` |
| どの資料から一般化したか | `SOURCES.md` |

## `AGENTS.md` の設計

慣例ファイル名は複数形の `AGENTS.md` とする。利用環境が別名を要求する場合だけ合わせる。

よい指示は次を含む。

- 適用範囲と、上位・下位指示の優先関係
- 自律実行してよい操作と、人の承認が必要な操作
- 最初に確認する最小情報
- 成果物の配置、正本、変更してはいけない原本
- リスクに応じた検証と完了条件
- 報告で区別すべき成功、失敗、未実行

プロジェクト配下の `AGENTS.md` は共通指針の全文を複製せず、実行コマンド、対象環境、固有の安全条件など差分だけを書く。長い設計理由や過去の失敗ログは別文書へ移す。

## `DESIGN.md` の設計

DESIGN は機能一覧ではなく、変更時に守るべき関係を示す。

- 目的と非目的
- 利用者、主要な利用経路、成功条件
- システム境界と信頼境界
- 状態モデル、正本、保存・復元・分岐
- 入出力契約、不変条件、失敗時の振る舞い
- 代替案と採用理由
- 検証方法と未検証領域

UI の場合は、画面名だけでなく、未保存状態、接続断、狭い画面、キーボード操作、長い値、空状態、エラーからの復帰を設計対象にする。

## 検証文書と引継ぎ文書

VALIDATION は主張ごとに条件と結果を持たせる。HANDOFF はその時点の正本、基準版、実行済みと未実行、直近の失敗、次の一手を持たせる。

過去の成功を今回の成功として書かない。再実行していない検証は「継承した結果」として明示する。引継ぎで判明した恒久的な教訓は、確認後に DESIGN、AGENTS、ガイドへ昇格させる。

## 文書を増やす判断

次のどれかを満たすときだけ新規文書を作る。

- 独立した読者や更新責任がある。
- 変化の速さが既存文書と大きく異なる。
- 同じ内容を複数箇所から参照する。
- 監査や再実行のため履歴を固定する必要がある。

それ以外は既存文書へ統合し、重複する規則を増やさない。

正本を別の場所へ投影する場合は、[同期手順](instruction-synchronization.md)で対象と方向を明示する。ファイルが揃うことと、エージェントが読み込む指針の適用範囲を区別する。
